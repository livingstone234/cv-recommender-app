# 5. LLM Output Schemas (Pydantic — Python's Zod)

## The core idea

LLMs produce text. Left alone, "extract this CV as JSON" can come back
malformed, missing fields, with a stray markdown code fence around it, or with a
`years_of_experience` field as the string `"5 years"` instead of the float `5.0`
you asked for. **Structured output** is the technique of forcing the LLM call
through a schema so the SDK either returns a validated, typed Python object, or
raises — never a "close enough" blob you have to defensively parse downstream.

If you've used [Zod](https://zod.dev) in a TypeScript/Next.js project to validate
API payloads or form input, **Pydantic is the direct Python equivalent** — same
idea (declare a schema, get a validated object or an error), different syntax
(Python type hints + class-based models vs Zod's `z.object({...})` chains).
LangChain's `.with_structured_output(SomeSchema)` is what wires a Pydantic class
into the LLM call — under the hood, for OpenAI/Gemini, this uses the provider's
native "tool calling" / JSON-mode feature so the model is constrained at
generation time, not just validated after the fact.

## `app/schemas/cv_schema.py` — what extraction must return

```python
from pydantic import BaseModel, Field
from typing import List, Optional

class Experience(BaseModel):
    company: str
    title: str
    start_date: Optional[str] = None
    end_date: Optional[str] = None
    summary: str
    achievements: List[str] = Field(default_factory=list)

class Education(BaseModel):
    institution: str
    degree: str
    field_of_study: Optional[str] = None
    graduation_year: Optional[str] = None

class ExtractedCV(BaseModel):
    full_name: str
    email: Optional[str] = None
    phone: Optional[str] = None
    headline: Optional[str] = Field(None, description="Current title / summary line")
    skills: List[str]
    years_of_experience: float
    experience: List[Experience]
    education: List[Education]
    certifications: List[str] = Field(default_factory=list)
```

Two things worth noticing:

- **Nested models compose.** `ExtractedCV.experience` is a `List[Experience]`, and
  `Experience` is its own `BaseModel`. Pydantic validates the whole nested
  structure recursively — a CV with an `experience` entry missing `company` fails
  validation for the *whole* extraction, which is exactly the "fail loud, not
  silent" behavior you want feeding into a downstream `improvement` prompt.
- **`Field(..., description=...)` is not just documentation.** LangChain forwards
  field descriptions into the schema definition sent to the LLM provider, so the
  model literally reads `"Current title / summary line"` as an instruction for
  what belongs in `headline`. This is a real lever for prompt-engineering *through
  the schema itself*, not just the system prompt.

## `app/schemas/improvement_schema.py` — the critique

```python
from pydantic import BaseModel
from typing import List

class Improvement(BaseModel):
    section: str      # e.g. "Summary", "Experience - Company X"
    issue: str         # what's wrong
    suggestion: str    # concrete rewrite / fix
    priority: str       # "high" | "medium" | "low"

class ImprovementReport(BaseModel):
    overall_score: int  # 0-100
    strengths: List[str]
    improvements: List[Improvement]
```

Note `priority` and `overall_score` are typed as plain `str`/`int` with a
comment describing the intended range/values, rather than a Python `Enum` or
`Literal["high", "medium", "low"]`. Using `Literal[...]` would be the stricter,
more "correct" choice — worth doing once the schema stabilizes, since it makes
invalid priorities a validation error instead of a silent string mismatch the
frontend has to defensively handle.

## `app/schemas/job_match_schema.py` — the recommendations

```python
from pydantic import BaseModel
from typing import List

class SkillGap(BaseModel):
    skill: str
    resource_name: str
    resource_url: str

class JobMatch(BaseModel):
    job_title: str
    match_score: int          # 0-100
    reasoning: str
    apply_links: List[str]    # e.g. LinkedIn/Indeed search URLs
    skill_gaps: List[SkillGap] = []

class JobMatchReport(BaseModel):
    matches: List[JobMatch]
```

Notice `apply_links` and `resource_url` are typed as plain `str`, but the actual
URLs are **never generated by the LLM** — see
[06-langchain-pipeline.md](06-langchain-pipeline.md#the-job-board-link-builder-deterministic).
The LLM is instructed to identify *what* job titles/skills to search for; a plain
Python function builds the *actual* URL from a known template. This avoids the
classic LLM failure mode of hallucinating a plausible-looking but broken/nonexistent
URL.
